이 폴더는 `run_all.py` 가 단계마다 남기는 실행 로그와 진행·결과 기록(`index.json`), 서빙 검증 증거 파일이 저장되는 곳이다.

# steps — 단계별 실행 기록

**결론**: 실행이 어떻게 끝났는지는 `index.json`(기계용)과 `python show_results.py`(사람용)로 본다.
**`run_all.py`는 시작할 때 이 폴더에서 README.md를 뺀 실행 기록을 지우므로**, 지난 실행 기록을 남기려면 먼저 다른 곳에 복사한다. 코드 수정 전 로그와 수정 후 로그를 섞어 검증 근거로 사용하지 않는다.

## 파일

| 파일 | 내용 |
|---|---|
| `{순번}_{단계 id}.txt` | 단계 하나의 화면 출력 전체 (예 `01_0.1.txt`, `44_6.6.txt`, `58_S.1.txt`, `62_C.txt`). 62단계 |
| `index.json` | 실행 모드(FULL/FAST)·상태·시작/종료 시각·단계별 상태·소요시간·로그 줄 수·**그 단계가 새로 쓴 표·그림·모델 파일 목록**·오류 위치·점검 결과·코드 파일 sha256(provenance)·라이브러리 버전 |
| `serving_verify_eval.json` · `serving_verify_deploy.json` | S.1 — 두 번들의 무결성·자가검증 결과 |
| `serving_replay_eval.csv` · `serving_replay_check.txt` | S.2 — 평가 번들로 9/1~9/14를 재생한 결과. FULL에서는 파이프라인의 메모리 예측과 비트 비교하고 제출 경보 라벨도 대조 |
| `serving_demo_history.csv` · `serving_demo_plan.csv` | S.3 — 예측 데모 입력(원자료 8/31~9/13 이력, 9/14 생산계획 — 계획에는 전력이 없다) |
| `serving_predict_eval_20210914.csv` · `serving_predict_deploy_20210914.csv` | S.3 — 9/14 익일 예측 결과. 배포 번들 쪽은 학습 구간 안의 날이라 **데모**다 |
| `serving_demo_plan_leak.csv` | S.3 — 누수 차단 시험 입력(계획에 대상일 전력 `평균` 열을 일부러 넣은 파일). 이 파일로 예측하면 종료코드 2(`PLAN_HAS_POWER`)로 거부되고 예측 파일이 생기지 않아야 정상이다 |
| `serving_unit_tests.txt` | S.4 — 단위·회귀테스트 출력. 실제 수집·통과·실패·skip 개수는 파일 끝 요약으로 확인 |
| `.run_all.lock` | 실행 중에만 있는 잠금 파일(같은 폴더에서 두 번 동시에 돌지 않게). 정상 종료하면 사라진다 |

`--skip-bundle`·`--skip-serving`·`--no-tests` 로 건너뛴 서빙 단계의 파일은 생기지 않는다.

## index.json 읽는 법

- `status`: `ok`(성공) · `failed`(어떤 단계가 실패 — `current` 와 그 단계의 `error` 에 `src/sNN_….py:줄` 위치) ·
  `interrupted`(Ctrl+C·멈춤 프롬프트의 q·서버 중지 신호로 중단) · `check_failed`(계산은 끝났지만 완료 점검 필수 항목 실패) ·
  `running`(실행 중이거나, 강제 종료로 기록이 끊김 — `show_results.py` 가 끊긴 기록이면 따로 알려 준다).
- `steps[*].report`: 그 단계가 뒷받침하는 보고서 절. `show_results.py` 가 이것으로 보고서 순서의 쪽을 만든다.
- `checks.hard` / `warn` / `info`: 완료 점검(C) 결과. hard 가 하나라도 실패하면 종료코드 3.

`status=ok`는 해당 실행에 포함된 단계가 완료됐다는 뜻이다. FAST 실행, 테스트 생략, 95% 유의성 기준 미충족을 별도로 확인한다. `--no-tests`로 끝난 실행을 테스트 통과로 표현하지 않으며, 90% 사후 보조분석만으로 95% 기본 기준을 통과했다고 해석하지 않는다.

현재 실행 계획은 코드 단계 57개 + 서빙·테스트 4개 + 완료 점검 1개로 총 62단계다. FULL 필수 산출물은 CSV 110개와 그림 39개이며 C가 확인한다. S.4는 `tests/` 전체를 실행한다.

이번 FULL 검증의 `status`는 `ok`이고 62단계가 모두 `ok`이며 생략된 단계는 없다. 필수 점검 15/15·보조 점검 4/4 통과, S.1 두 번들 검증 통과, S.2 336행 메모리 비교 불일치 0건, S.3 eval·deploy 각 24행 데모 및 누수 입력 종료코드 2, S.4 `123 passed in 17.42s`가 기록됐다. 본 실행 26분 06초는 별도 사전 계산한 6.6 체크포인트를 재사용한 시간이며 사전 계산 시간을 포함하지 않는다.

6.6 레짐 변형의 체크포인트는 이 로그 폴더가 아니라 기본 `.cache/regime_cv` 또는 `$KAMP_WORK_DIR/regime_cv`에 둔다. 소스·입력·설정·런타임·바이너리 지문과 NPZ 해시·완료 JSON으로 검증된 결과만 재사용한다. 재시도 후에도 실패한 요청은 성공으로 처리하지 않는다. 재실행하면 앞선 단계는 다시 계산하며 작업 캐시는 제출·결과 ZIP에 넣지 않는다.

## 로그에만 남는 값

표로 저장되지 않고 **단계 로그에만** 나오는 값이 있다. 보고서에 인용할 때는 이번 실행의 로그에서 읽는다:
- 학습된 모델의 336시간 배치 추론시간(6.4 단계 로그, 10회 중앙값; 동봉 Windows 재실행 로그 0.0267초, 원 제출 실행 0.0307초). 재학습 시간과 구분하며 환경·부하에 따라 달라진다. 저장 번들 검증 중의 별도 예측 측정은 10.5 단계 로그에 있다.
- 선택된 한글 폰트 이름(0.6 단계 로그의 '실행 환경' 요약. 같은 요약의 라이브러리 버전은 `outputs/tables/env_versions.csv` 에도 저장된다).

이 값들은 실행하는 컴퓨터·부하에 따라 달라진다.

## 경로 가림

로그와 `serving_*` 파일에는 실행 폴더·홈 폴더·사용자 이름이 남지 않도록 쓸 때 가린다:
패키지 폴더 → `.`, 홈 폴더 → `~`, 파이썬 설치 폴더 → `<python>`, 임시 폴더 → `<tmp>`, 사용자 설치 폴더(`pip --user`) → `<user-site>`,
그 밖의 사용자 폴더 경로는 사용자 이름 자리를 `<사용자>`·`<홈>` 으로 바꾼다. 색상 코드는 지우고 줄바꿈은 LF 로 맞춘다.
(예: 라이브러리 경고에 보이는 `<python>…site-packages…` 는 파이썬 설치 폴더 안의 라이브러리 파일이다.)
그래서 이 폴더는 그대로 결과 묶음(`python run_all.py --pack-results`)에 들어간다(잠금 파일과 이 README 제외).
